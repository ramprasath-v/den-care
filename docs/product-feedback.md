# CareCircle product feedback

This feedback records tools and services actually used while building and verifying CareCircle. It is based on the repository's deployment records and [friction log](friction-log.md).

| Tool, API, or SDK | What CareCircle used it for | What worked well | What needs improvement | Onboarding experience | Use again? |
| --- | --- | --- | --- | --- | --- |
| Amazon Bedrock with Claude Sonnet 4.6 | Advisory Supervisor planning and bounded triage signal extraction through the US inference profile | The Strands integration returned useful specialist selections while deterministic code retained safety and approval decisions. Live logs confirmed real model invocation. | Model and cross-region inference-profile ARN permissions were easy to scope incorrectly. Clearer examples for profile IDs and all required foundation-model ARNs would reduce setup time. | Model discovery and a live invoke check were necessary before deployment. | Yes, for bounded reasoning behind deterministic policy controls. |
| Amazon Bedrock AgentCore Runtime and CLI | Hosted the IAM-authenticated ARM64 MCP container and endpoint | Managed runtime, IAM authorization, container deployment, CloudWatch integration, and the MCP protocol fit the project well. | Deployment required several control-plane permissions that were discovered through CloudFormation rollback: endpoint lifecycle, workload identity parent/child resources, tagging, service-linked-role creation, and generated helper resources. A complete least-privilege deployment-policy reference and preflight would help. | The runtime itself was straightforward after the deployment prerequisites were understood; failed-stack recovery was the longest part. | Yes, with a reviewed deployment role and synthesized-name preflight. |
| Strands Agents | Implemented the Supervisor's agents-as-tools advisory plan | Specialist tools composed cleanly, and callbacks could be disabled so prompts were not copied into application logs. | More examples connecting nested agent/tool lifecycle events to privacy-safe application progress would help voice and UI applications. | Fast once the model profile and tool schemas were configured. | Yes, especially where deterministic code owns mutations. |
| Python MCP SDK | Exposed four typed public tools over Streamable HTTP | `FastMCP` made the tool surface small and testable, and negotiated protocol `2025-11-25` successfully with AgentCore. | Protocol-version and transport compatibility deserve prominent end-to-end examples for hosted runtimes. | The basic server was quick; hosted IAM invocation required a separate AWS client path. | Yes. |
| DynamoDB | Stored synthetic profiles, events, incidents, and action-ledger records | On-demand tables, conditional writes, and strongly consistent reads supported durable multi-turn state and idempotency. | Demo generation boundaries and reset semantics remained application responsibilities and required careful testing. | Table creation and Boto3 access were direct. | Yes for small event/state records. |
| Amazon SNS | Published approved caregiver alerts to a Lambda-backed synthetic inbox | Message IDs and application idempotency made duplicate-delivery checks clear. | Local/demo documentation should make explicit that a Lambda subscription is a synthetic inbox and not a real caregiver delivery. | Simple after the topic and Lambda permission were connected. | Yes for approved notification workflows. |
| EventBridge Scheduler | Created one-shot follow-up checks | One-shot schedules with automatic deletion matched the follow-up requirement without a polling service. | The execution-role trust condition was evaluated against the schedule-group ARN, not the individual schedule ARN expected during the first implementation. The trust-policy documentation should foreground this exact resource shape. | Creation was easy after correcting the role trust. | Yes. |
| AWS Lambda | Received synthetic SNS alerts and executed scheduled follow-ups | A small inline function was sufficient and integrated cleanly with DynamoDB, SNS, and Scheduler. | CloudFormation rollback can retain its log group; clearer cleanup visibility would help failed deployments. | Straightforward. | Yes for this bounded event handler. |
| AWS App Runner and Amazon ECR | Hosted the existing Python/browser container over public HTTPS | Produced a secure microphone-compatible URL without a load balancer, domain purchase, VPC, or NAT gateway. The instance role kept AWS credentials out of browser JavaScript. | Image rollout and service readiness are asynchronous, so deployment output should expose the active digest and readiness together. | Low-friction once the immutable image was pushed. | Yes for a short-lived public demo. |
| Amazon CloudWatch Logs | Stored runtime logs and supplied privacy-safe progress events | Session-correlated metadata supported real agent/tool counters without logging health utterances or model reasoning. | Delivery lag varied enough to dominate some UI turns. A lower-latency managed progress stream or documented tailing pattern would improve interactive applications. | Logging was automatic; reliable live progress required bounded settling and deduplication. | Yes for audit evidence; use a direct event channel for latency-sensitive UI progress. |
| Amazon Transcribe Streaming | Converted browser-generated 16 kHz mono PCM to text | The same transcription result entered the typed conversation handler, preserving session and approval state. | The Python streaming SDK was a separate dependency and its errors initially surfaced only as a generic HTTP failure. Dependency/version guidance and structured upstream errors would help. | PCM avoided a native audio converter, but microphone and secure-origin behavior still needed browser testing. | Yes. |
| Amazon Polly | Synthesized deterministic natural voice summaries | Neural speech was reliable, and server-side synthesis kept credentials out of the browser. | Applications need clear sequencing guidance so playback does not begin before state refresh and progress completion. | Very quick through Boto3. | Yes. |
| CloudFormation, AWS CDK, CodeBuild, IAM, and KMS | Defined, built, authorized, and encrypted the AgentCore and application stacks | Repeatable templates, ARM64 managed builds, named roles, and encrypted resources produced a reviewable deployment. | Generated physical-name truncation, composite resource-handler permissions, managed-policy replacement properties, KMS rollback behavior, and temporary control-plane breadth caused repeated failed-stack recovery. Synthesis-aware permission generation and better rollback diagnostics would materially improve onboarding. | Powerful but substantially more involved than the runtime application work. | Yes, with an isolated deployment role and cleanup plan. |

## Overall feedback

The AWS combination supported a credible multi-service agentic workflow rather than a single model call: Bedrock and Strands planned, AgentCore hosted MCP, DynamoDB preserved state, SNS and Scheduler/Lambda handled approved and delayed actions, and App Runner, Transcribe, Polly, and CloudWatch provided the voice demo. The strongest parts were managed HTTPS hosting, IAM-based server-to-server access, typed MCP tools, and composable event services. The main improvement opportunity is deployment onboarding: a single authoritative lifecycle-permission matrix and generated-name preview would have prevented most failed CloudFormation attempts.
